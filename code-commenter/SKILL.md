# Code Commenter

## 目标与范围

为代码补充**准确、简洁、可维护的简体中文注释**，主要解释设计意图、业务规则、约束和非显而易见的实现原因，而不是逐行翻译代码。

适用操作：新增注释、优化已有注释、检查注释质量、仅解释代码。除非用户明确另行授权，使用本 Skill 编辑时**只允许更改注释**。

## 语言规则：按需加载

在生成或修改注释前，先识别目标文件语言，并读取相应参考文件：

- Java（`.java`，含 Spring / Javadoc 场景）：读取 [references/java.md](references/java.md)。
- 前端（`.js`、`.jsx`、`.ts`、`.tsx`、`.vue`、`.html`、`.css`、`.scss` 等）：读取 [references/frontend.md](references/frontend.md)。
- 跨 Java 与前端的改动：两份都读取，分别按文件语言应用规则。
- 未覆盖的语言：仅应用本文件的通用原则，遵循实际语法和仓库规范；不套用 Java 或前端专有标签。

参考文件只提供语言特定规范，不能覆盖本文件的安全边界和用户的明确要求。

## 通用注释原则

1. **中文优先**：所有新增注释默认使用简体中文；改写已有注释时优先优化为自然、准确的简体中文。若用户明确指定其他语言，则遵从用户要求。
2. **术语准确**：类名、函数名、字段名、API、协议名、标准名称、框架术语保留原文；不要生硬翻译标识符。
3. **解释 Why**：优先描述“为什么这样做”、约束、业务规则及边界条件；代码本身已经清楚表达的行为无需复述。
4. **必要且精炼**：避免注释密度过高，不为简单赋值、自解释变量、显然的分支和常规 Getter/Setter 强行加注释。
5. **基于证据**：通过调用方、模型、测试、业务文档和现有约定理解代码。不能确定的业务含义不得编造；提出待确认项。
6. **保持一致**：注释必须符合当前代码行为，不复制过期的描述；已有准确且有价值的注释应予以保留。
7. **尊重仓库风格**：在简体中文默认要求下，延续项目既有的缩进、注释格式、术语表和文档工具约定。发生冲突时，用户明确指令优先；不确定时说明冲突。
8. **保护特殊注释**：不得擅自修改许可证/版权声明、第三方声明、代码生成标记、lint/编译器/格式化/覆盖率指令、source map 标记及其他可能影响工具行为的注释。

## 执行模式

- `smart`（默认）：只对需要说明的代码补充或优化注释。
- `full`：完善有文档价值的类型、公开接口与复杂方法注释，仍避免冗余。
- `business`：重点解释业务分支、状态转换、领域不变量及特殊处理依据。
- `review`：只检查和提出建议，**不修改文件**。

用户未指定模式时使用 `smart`；仅询问“这段代码是什么意思”时解释，不直接编辑。

## 执行工作流

1. **界定范围**：明确目标文件/代码段、模式及是否允许编辑；不自行扩大修改范围。
2. **读取上下文**：查看代码、相关调用链、类型定义、测试及项目注释风格。缺少上下文时仅编写可直接验证的说明。
3. **加载语言规则**：按文件类型读取对应 `references/` 文件。混合文件按语法区域应用正确注释语法。
4. **识别注释点**：优先选择公开契约、复杂算法、业务限制、异常与边界、并发/性能取舍；跳过显而易见的语句。
5. **生成或优化**：以简体中文说明意图，尽可能贴近被说明代码；清理确定错误、重复或过时的普通说明注释。
6. **执行核查**：确认语法合法、注释与实现一致，并且未改变可执行代码、配置、签名、标识符或特殊指令。
7. **交付结果**：简要说明新增/优化/删除的注释和不确定项；能编辑仓库时优先展示注释相关差异，否则给出可复制的代码片段。

## 不可跨越的边界

- 只因注释任务而运行时，不修改程序逻辑、导入、类型定义、测试、配置、依赖和文件结构；不为“让注释成立”而改代码。
- 不重排无关代码和格式，不更改行尾、编码或原有语义；尤其不要改动会影响编译/工具行为的特殊注释。
- 不编造业务需求、异常承诺、性能保证或并发安全性。
- 如果发现实现疑似有 Bug，报告问题及建议，但不擅自修复。
- `review` 模式绝不写入文件。

## 交付验收

- [ ] 中文自然准确，没有逐行翻译或多余注释。
- [ ] 已读取适用语言的参考文件，注释语法与工具链兼容。
- [ ] 业务原因均有代码或上下文证据，存疑处明确标识。
- [ ] 保留有价值的既有注释和受保护指令。
- [ ] 修改仅限普通注释；无非注释代码变更。
- [ ] 已给出精简的修改摘要或审查结论。
